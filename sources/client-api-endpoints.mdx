# Client API Endpoints (Deep Guide)

This page is the endpoint-level implementation guide.
Use it with:

- `Client API (Generated)` in the left nav for schema-level fields/examples
- `/sources/client-api-reference` for compact endpoint catalog

## Global rules for every endpoint

### Authentication

All endpoints require:

```http
Authorization: Bearer omni_live_...
```

### Request correlation

Send `X-Request-Id` on every request and log OMNI's echoed value.

For failures:

- REST: `error.request_id`
- Hosted MCP: `error.data.request_id`

### Idempotency

Required for write-like operations:

- `POST /v1/mcp/invoke`
- hosted MCP `tools/call` via `POST /mcp`

If you retry, reuse the same `Idempotency-Key`.

### Billing

- `2xx/3xx` billable
- `4xx/5xx` non-billable
- idempotency replays are not double-billed

## Endpoint playbooks

## `GET /v1/health`

Use when:

- validating key + allowlist access
- validating basic request/response and request-id plumbing

Expected success shape:

- `object = health`
- `status = ok`
- `mode = live|test`

Common failures:

- `missing_api_key`
- `invalid_api_key`
- `auth_rejected`

## `GET /v1/openapi.json`

Use when:

- generating clients
- diffing contracts in CI
- powering API explorer workflows

Integration note:

- pin and diff this schema in CI before upgrading pinned `Omni-Version`

## `GET /v1/fred/search`

Use when:

- searching for relevant economic time-series metadata

Inputs:

- `q` required
- `limit` optional, bounded

Production patterns:

- cache short-lived search results by normalized `(q, limit)`
- enforce local query length/range validation to reduce `400` churn

Common failures:

- `missing_q`
- `insufficient_scope` (missing `fred.read`)
- `fred_invalid_request` / `fred_upstream_error`

## `GET /v1/fred/series/{series_id}`

Use when:

- fetching observations for charting/analysis

Inputs:

- `series_id` required
- optional date bounds and limit

Production patterns:

- cache by `(series_id, observation_start, observation_end, limit)`
- protect downstream chart jobs from sparse/empty result sets

Common failures:

- `missing_series_id`
- `insufficient_scope`
- `fred_invalid_request` / `fred_upstream_error`

## `GET /v1/mcp/tools` (legacy compatibility)

Use when:

- maintaining legacy clients during migration

Required scope:

- `mcp.tools.read`

Migration recommendation:

- move to hosted MCP `tools/list` as canonical path

## `POST /v1/mcp/invoke` (legacy compatibility)

Use when:

- maintaining legacy clients that are not JSON-RPC aware

Required headers:

```http
Authorization: Bearer omni_live_...
Idempotency-Key: idem_...
Content-Type: application/json
```

Common failures:

- `missing_idempotency_key`
- `invalid_json`
- `invalid_payload`
- `unknown_tool`
- `idempotency_conflict`
- `mcp_invocation_failed`

Migration recommendation:

- move to hosted MCP `tools/call`

## Hosted MCP transport (`/mcp` and `/sse`)

Hosted MCP is canonical for MCP clients.

If you are not building around MCP tooling, prefer REST endpoints.

### `POST /mcp`

Core methods:

- `initialize`
- `notifications/initialized`
- `tools/list`
- `tools/call`
- `ping`

Required scopes by method:

- `tools/list`: `mcp.tools.read`
- `tools/call`: `mcp.invoke` + tool scope

Idempotency:

- required for `tools/call`
- optional/unused for read-only methods

### `GET /mcp`

Use only when the client expects a stream transport channel.
Most integrations can use `POST /mcp` only.

### `DELETE /mcp`

Close an active hosted session context.
Use explicitly in long-lived client processes during shutdown.

### `GET /sse`

Compatibility transport for clients expecting SSE bootstrap.
Prefer `/mcp` for net-new integrations.

## Endpoint readiness checklist

- [ ] Explicit scope map per endpoint/method
- [ ] Request ID propagation + logging verified
- [ ] Idempotency implemented where required
- [ ] Retry/backoff policy aligned with `/sources/client-api-retries`
- [ ] Error handling based on machine fields only (`error.type`, `error.code`, JSON-RPC codes)
- [ ] Billing behavior validated for success/failure/replay

## Failure triage order

1. Confirm auth key validity (`401` vs `403`).
2. Confirm required scopes (`Omni-Required-Scopes` when present).
3. Confirm payload shape and idempotency.
4. Confirm upstream/transient behavior and retry posture.
5. Escalate with `request_id` and endpoint/method context.
