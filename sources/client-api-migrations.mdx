# Client API Migrations

This page defines the migration contract for OMNI Client API and hosted MCP.

If you operate production integrations, treat this page as policy.

## Migration north stars

1. Prefer additive changes (new fields/endpoints/tools).
2. Never ship hidden breaking behavior on a pinned version.
3. Keep retries safe with idempotency.
4. Keep request correlation intact with request IDs.

## Lifecycle guarantees (v1.5 baseline)

| Change type | Compatibility guarantee | Communication requirement | Minimum migration window |
| --- | --- | --- | --- |
| Additive | Backward compatible | Changelog entry | none |
| Behavioral (non-breaking) | Existing shapes preserved | Changelog entry + rationale | 14 days recommended |
| Deprecation | Old route/tool stays functional during sunset | `Deprecation` + `Sunset` headers + migration guide | 180 days target |
| Breaking | New versioned surface required | Changelog + migration guide + compatibility matrix update | 90 days target after replacement launch |

## Deprecation timeline template

Use this timeline for any deprecated surface:

- `T-90`: announce replacement and migration guide
- `T-60`: begin warning alerts/metrics on legacy usage
- `T-30`: enforce deprecation headers and customer outreach
- `T-7`: freeze new dependencies on deprecated surface
- `T-0`: execute sunset only after migration SLO gates pass

## Breaking-change release process

1. Introduce replacement first.
2. Publish concrete before/after examples.
3. Dual-run old and new paths through at least one billing cycle.
4. Add deprecation headers with explicit sunset date.
5. Sunset only after migration success and rollback confidence are documented.

## Migration guide: legacy MCP routes to hosted MCP

Legacy routes:

- `GET /v1/mcp/tools`
- `POST /v1/mcp/invoke`

Canonical target:

- `POST /mcp` with JSON-RPC methods

### Mapping

| Legacy route | Hosted MCP equivalent |
| --- | --- |
| `GET /v1/mcp/tools` | `POST /mcp` with `method=tools/list` |
| `POST /v1/mcp/invoke` | `POST /mcp` with `method=tools/call` |

### Required sequence for hosted MCP

1. call `initialize`
2. send `notifications/initialized`
3. use `tools/list`
4. use `tools/call`

### Non-negotiable migration checks

- `Idempotency-Key` on every `tools/call`
- scoped key includes `mcp.tools.read`, `mcp.invoke`, and tool scopes (for example `fred.read`)
- retry policy updated for JSON-RPC errors
- request-id logging upgraded for JSON-RPC `error.data.request_id`

## Migration guide: unscoped keys to scoped keys

Recommended minimum scope set for MCP + FRED:

```json
["mcp.tools.read", "mcp.invoke", "fred.read"]
```

If you hit `403 insufficient_scope`, debug in this order:

1. key scope assignment
2. `Omni-Required-Scopes` header
3. method/tool scope contract

## Migration guide: version pin upgrades (`Omni-Version`)

Pinning example:

```http
Omni-Version: 2026-02-18
```

Upgrade runbook:

1. review changelog and migration notes
2. run integration tests against new pin
3. canary by key/environment
4. monitor error and billing drift
5. promote gradually
6. keep rollback to previous pin until stability clears

## Rollback criteria (mandatory)

Rollback immediately if any condition is sustained:

1. auth/scope failure spike (`401`/`403`)
2. idempotency conflict spike (`409`)
3. invocation error spike (`mcp_invocation_failed`, `mcp_internal_error`)
4. unexpected billing drift

## Copy/paste production migration checklist

- [ ] endpoint/tool mapping verified
- [ ] scope set updated and tested
- [ ] idempotency behavior verified under retries
- [ ] request-id logging verified end-to-end
