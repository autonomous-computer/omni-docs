# Client API Errors

OMNI Client API uses a stable, machine-readable error contract across REST (`/v1/...`) and hosted MCP (`/mcp`).

This page is the authoritative **v1 error-code registry** for integrations.

## Stability guarantees

- `error.type` and `error.code` are stable and safe for programmatic branching.
- `error.message` is human-readable and may change; never parse it.
- `error.request_id` (or JSON-RPC `error.data.request_id`) is the support/debug join key.
- During internal beta, new codes may be added. Existing codes are not silently repurposed.

## REST error envelope

```json
{
  "error": {
    "type": "invalid_request | auth_error | permission_error | rate_limit_error | api_error",
    "code": "machine_readable_code",
    "message": "Human-readable message",
    "request_id": "req_xxx"
  }
}
```

## Diagnostic headers to always log

- `X-Request-Id`: request correlation key
- `Omni-Required-Scopes`: present on some `403 insufficient_scope`
- `Idempotency-Replayed: true`: served from idempotency replay cache
- `Retry-After`: present on `429` responses

## HTTP category mapping

| `error.type` | Typical HTTP status |
| --- | --- |
| `invalid_request` | 400, 409 |
| `auth_error` | 401, 403 |
| `permission_error` | 403 |
| `rate_limit_error` | 429 |
| `api_error` | 5xx |

| --- | --- |

## Hosted MCP JSON-RPC errors

Hosted MCP uses JSON-RPC 2.0 error shape:

```json
{
  "jsonrpc": "2.0",
  "id": 3,
  "error": {
    "code": -32001,
    "message": "Unauthorized",
    "data": {
      "omni_code": "invalid_api_key",
      "request_id": "req_123"
    }
  }
}
```

### JSON-RPC code mapping

| JSON-RPC code | Meaning | Typical source |
| --- | --- | --- |
| `-32700` | Parse error | malformed JSON request body |
| `-32600` | Invalid request | invalid JSON-RPC object (missing/invalid method) |
| `-32601` | Method not found | unsupported MCP method |
| `-32602` | Invalid params | missing tool name, missing idempotency key, invalid request params |
| `-32001` | Auth/permission | mapped `auth_error` / `permission_error` |
| `-32002` | Rate limit | mapped `rate_limit_error` |
| `-32603` | Internal error | mapped `api_error` and unhandled internal failures |

### `omni_code` presence rules

- When errors originate from the shared OMNI REST error system, `error.data.omni_code` is present.
- Pure transport-level JSON-RPC validation errors (for example malformed method/payload before handler routing) may omit `omni_code`.
- `error.data.request_id` is always present on hosted MCP errors.

## Retry policy

| Condition | Retry? | Rule |
| --- | --- | --- |
| `429 rate_limit_exceeded` / JSON-RPC `-32002` | Yes | Honor `Retry-After`; otherwise bounded exponential backoff + jitter |
| `503 auth_backend_unavailable` / `503 invalid_control_plane_response` | Yes | Bounded backoff + jitter |
| `409 idempotency_conflict` | Yes | Retry with same idempotency key |
| `400 invalid_request*` / JSON-RPC `-32602` | No | Fix request first |
| `401/403` auth/scope | No | Fix key/scopes first |
| `500 mcp_internal_error` / JSON-RPC `-32603` | Yes | Retry idempotently and escalate if persistent |

## Deterministic client handling algorithm

1. Parse machine fields only.
2. If HTTP is `429` or `5xx` (or JSON-RPC is retryable category), run bounded retry.
3. For write-like calls, reuse the same idempotency key on retries.
4. If non-retryable, bubble structured error with request ids.
5. Log `request_id`, endpoint/method, and idempotency key together.
