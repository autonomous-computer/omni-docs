# Webhook Operations Handbook

This page is the operational companion to `/sources/client-api-webhooks`, which defines the webhook **contract**.

If you run webhooks in production, treat the guidance below as non-optional.

## Goals

Your receiver must be:

- secure (signature verification when enabled)
- replay-resistant (timestamp window)
- idempotent (dedupe by `event.id`)
- fast (ack quickly, do work asynchronously)
- observable (metrics + request IDs)

## Receiver architecture (recommended)

1. Ingress handler: read headers and raw body bytes, verify signature (if present), enforce timestamp tolerance.
2. Durable queue: enqueue the event payload and metadata.
3. Immediate ACK: return `2xx` once enqueued.
4. Worker: dedupe by `event.id`, execute business logic, record success/failure.

## HTTP response rules

- Return `2xx` when you have durably accepted the event.
- Return `4xx` only for permanent failures (misconfiguration, invalid secret, invalid payload shape).
- Return `5xx` only when you want OMNI to treat the delivery as transient failure.

## Dedupe strategy

Use `event.id` as the dedupe key.

Recommendations:

- store processed IDs for at least 7 days
- store payload hash to detect unexpected duplicates with different bodies

## Observability

Log and emit metrics for:

- `X-Request-Id` (ingress request)
- `event.id`
- `event.type`
- `event.requestId` (originating OMNI request, when present)
- signature verified? (boolean)
- handler latency (p50/p95)

## Internal beta caveats

During internal beta:

- OMNI may deliver webhook events without a signature if signing is not enabled for your account/environment.
- Automatic retry loops may not be enabled yet.

Build your receiver as if retries already exist. When retries turn on, you should not need to change your code.

## Common failure modes (and fixes)

### Signature verification fails intermittently

Almost always caused by verifying against a parsed JSON body instead of the raw bytes.

Fix:

- verify against `raw_body` exactly as received over HTTP

### Duplicate processing

Caused by missing dedupe or deduping on `X-Request-Id` instead of `event.id`.

Fix:

- dedupe on `event.id`

### Slow ACKs and timeouts

Caused by doing business logic synchronously in the webhook handler.

Fix:

- enqueue, then ACK

## Practical framework tips

### Express / Node

- Use a raw body middleware for the webhook route (do not use `express.json()` directly for this route).
- Capture the raw bytes and pass them into signature verification.

### Next.js route handlers

- Read the raw request body as `Buffer` / `Uint8Array`.
- Verify before calling `request.json()` if you need to.

### FastAPI

- Use `await request.body()` to get raw bytes.
- Verify signature before parsing JSON.

## Operational runbooks (copy these into your on-call playbooks)

### 1) Signature verification failures

Signals:

- sudden spike in `4xx` responses from your receiver
- log lines like “invalid signature” or “event outside replay window”

Root causes:

- verifying against parsed JSON instead of raw bytes
- a proxy or middleware is mutating body bytes (gzip, whitespace, charset)
- the signing secret is incorrect or rotated out of sync
- clock drift between your server and reality

Actions:

- confirm you verify `Omni-Signature` against `${Omni-Timestamp}.${raw_body}` bytes exactly
- confirm the header values are read as strings without trimming
- enforce NTP and alert if drift exceeds 30s
- if you rotate secrets, overlap validity windows and deploy receiver changes before rotating

### 2) Duplicate processing

Signals:

- business side effects executed multiple times per `event.id`

Root causes:

- missing dedupe store
- deduping on `X-Request-Id` instead of `event.id`
- processing is not idempotent (database writes without unique constraints)

Actions:

- enforce dedupe by `event.id` (store for 7+ days)
- add unique constraints where possible (idempotency at the database layer)
- record payload hash to detect “same id, different body” anomalies

### 3) Receiver latency or timeouts

Signals:

- elevated request duration
- elevated `5xx` from your receiver
- ingress CPU spikes

Root causes:

- doing business logic inline in the webhook handler
- synchronous third-party calls in the handler path
- slow queue writes or deadlocks

Actions:

- move work behind a queue and acknowledge after enqueue
- add a hard timeout to the ingress handler (example: 2s) and fail fast with `5xx` if the queue is unavailable
- protect downstream workers with bounded concurrency

### 4) Poison-pill events

Signals:

- the same event repeatedly fails in your worker
- DLQ growth

Actions:

- route failed events to a DLQ after N attempts
- add a manual replay tool that can re-run a DLQ message after code fixes
- log `event.id`, `event.type`, and `event.requestId` for every failure

## What to log (minimum viable observability)

On every inbound delivery:

- `X-Request-Id`
- `event.id`
- `event.type`
- `event.requestId` (when present)
- signature present? (boolean)
- signature verified? (boolean, when present)
- handler latency (ms)
- queue enqueue result (ok/fail)

On the worker:

- processing latency by `event.type`
- success/fail counts by `event.type`
- DLQ counts

## Load shedding and backpressure

If your queue is down or saturated, it is safer to return `5xx` (transient) than to accept and drop events.

Recommended posture:

- fail closed when you cannot durably enqueue
- scale workers independently of ingress
- cap concurrency per event type (avoid stampeding)
