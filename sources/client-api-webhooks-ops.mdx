# Webhook Operations Handbook

This page is the operations companion to `/sources/client-api-webhooks` (contract/spec).

If you run webhooks in production, this page defines the minimum reliability and security posture.

## Operating model

Your receiver must be:

- secure: verify signature (when enabled) and enforce replay window
- idempotent: dedupe by `event.id`
- durable: enqueue before ACK
- observable: emit request/event-level telemetry
- recoverable: support replay and DLQ handling

## Reference architecture

1. Ingress handler receives raw body + headers.
2. Signature/timestamp checks run before JSON parse.
3. Payload is persisted to queue/storage.
4. Handler returns `2xx` immediately.
5. Worker processes idempotently and records outcome.

## Webhook payload and correlation fields

Minimum fields your pipeline should persist:

- `event.id`
- `event.type`
- `event.created`
- `event.requestId` (originating OMNI API request)
- ingress `X-Request-Id`
- signature verification result
- enqueue and processing timestamps

## HTTP response policy

- return `2xx` only after durable enqueue
- return `4xx` only for permanent validation failures
- return `5xx` for transient infrastructure failures

## Signature verification baseline

When signing is enabled, verify against raw bytes:

`HMAC_SHA256(secret, "{Omni-Timestamp}.{raw_body}")`

Required controls:

- enforce replay tolerance (default 300s)
- constant-time signature comparison
- strict raw-body verification (never parsed JSON)
- dual-secret verification during rotation window

### TypeScript (Node) verification snippet

```ts
import crypto from "node:crypto";

export function verifyOmniSignature(opts: {
  secret: string;
  timestamp: string;
  signature: string;
  rawBody: Buffer;
  toleranceSeconds?: number;
}) {
  const tolerance = opts.toleranceSeconds ?? 300;
  const ts = Number(opts.timestamp);
  if (!Number.isFinite(ts)) throw new Error("invalid Omni-Timestamp");

  const age = Math.abs(Date.now() / 1000 - ts);
  if (age > tolerance) throw new Error("event outside replay window");

  const payload = Buffer.concat([Buffer.from(`${opts.timestamp}.`), opts.rawBody]);
  const expectedHex = crypto.createHmac("sha256", opts.secret).update(payload).digest("hex");
  const expected = Buffer.from(expectedHex, "hex");
  const provided = Buffer.from(opts.signature, "hex");
  if (expected.length !== provided.length) throw new Error("invalid signature");
  if (!crypto.timingSafeEqual(expected, provided)) throw new Error("invalid signature");
}
```

### Python verification snippet

```python
import hashlib
import hmac
import time


def verify_omni_signature(*, secret: str, timestamp: str, signature: str, raw_body: bytes, tolerance_seconds: int = 300) -> None:
    ts = int(timestamp)
    if abs(int(time.time()) - ts) > tolerance_seconds:
        raise ValueError("event outside replay window")

    payload = (timestamp + ".").encode("utf-8") + raw_body
    expected = hmac.new(secret.encode("utf-8"), payload, hashlib.sha256).hexdigest()
    if not hmac.compare_digest(expected, signature):
        raise ValueError("invalid signature")
```

## Dedupe and idempotency contract

- dedupe key: `event.id`
- retention window: minimum 7 days (recommended 30 days)
- reject duplicates before worker business logic
- enforce downstream idempotency by unique keys on business side effects

## Retry + DLQ policy (public-beta-ready target)

Recommended retry schedule for transient failures:

| Attempt | Delay |
| --- | --- |
| 1 | immediate |
| 2 | 1 minute |
| 3 | 5 minutes |
| 4 | 30 minutes |
| 5 | 2 hours |
| 6 | 12 hours |

After terminal retry failure:

- route to DLQ with full metadata
- require explicit operator replay decision

## Current internal-beta retry behavior (live)

For configured webhook endpoints, OMNI currently retries transient delivery failures with bounded attempts.

- retryable classes: network failure (`status=0`), `408`, `429`, `5xx`
- default max attempts: `3`
- default base delay: `500ms`
- backoff: exponential with jitter

Delivery diagnostics expose:

- `attempts`
- `retryExhausted`

Use these fields to separate transient failures from exhausted retries in incident triage.

DLQ record minimum fields:

- `event.id`, `event.type`
- failure class (`signature`, `validation`, `dependency`, `timeout`, `unknown`)
- last error payload/stack
- first seen / last attempted timestamps
- replay count

## SLO targets (recommended)

- ingress ACK p95 `< 500ms`
- successful processing rate `>= 99.9%`
- replay success rate `>= 99%`
- sustained DLQ growth `= 0`

## Incident response matrix

| Symptom | Likely cause | Immediate action | Hardening follow-up |
| --- | --- | --- | --- |
| Signature failures spike | wrong secret, raw-body mutation, clock skew | fail closed, validate NTP + secret, roll back receiver changes | add dual-secret rollout and fixture tests |
| Duplicate side effects | dedupe gap or non-idempotent worker | pause processing, enforce event-id lock | add DB uniqueness and idempotent writes |
| ACK timeout spike | blocking work in ingress path | move to queue-first ACK | add timeout budgets and ingress SLO alerts |
| Rising DLQ volume | poison-pill events or dependency outage | isolate failing class, replay after fix | typed validators + automated classifier |

## Replay runbook

1. Identify failed `event.id` and root-cause class.
2. Patch code/config.
3. Replay via replay tooling with original `event.id` context.
4. Verify no duplicate side effects.
5. Close incident with preventive action and monitor window.

## Beta caveat

In internal beta, signing and retry posture may vary by account/environment configuration. Build receiver behavior as if full signing and at-least-once retries are always active.

## Production readiness checklist

- [ ] raw-body signature verification tests pass
- [ ] replay-window checks enabled
- [ ] dedupe store in persistent DB/redis
- [ ] queue-first ingress and thin handler
- [ ] DLQ + replay tooling implemented
- [ ] alerts on signature failures, enqueue failures, DLQ growth
- [ ] runbook includes `event.id` + `request_id` correlation steps
