# Webhook Operations Handbook

This page is the operations companion to `/sources/client-api-webhooks` (contract/spec).

If you run webhooks in production, this page defines the minimum reliability and security posture.

## Design goals

Your receiver must be:

- secure: verify signature (when enabled) and enforce replay window
- idempotent: dedupe by `event.id`
- durable: enqueue before ACK
- observable: emit request/event-level telemetry
- recoverable: support replay and DLQ handling

## Reference architecture

1. Ingress handler receives raw body + headers.
2. Signature and timestamp checks run before parsing JSON.
3. Payload enqueued durably.
4. Handler returns `2xx` immediately.
5. Worker processes idempotently and records outcome.

## HTTP response policy

- return `2xx` only after durable enqueue
- return `4xx` for permanent failures (bad secret, invalid shape)
- return `5xx` for transient failures (queue outage, dependency outage)

## Signature verification

When signing is enabled, verify against raw bytes:

`HMAC_SHA256(secret, "{Omni-Timestamp}.{raw_body}")`

Minimum controls:

- enforce timestamp tolerance (default 300s)
- use constant-time comparison
- reject missing/invalid signature in signed environments

## Secret rotation runbook

1. Deploy receiver that accepts primary + secondary secrets.
2. Rotate OMNI signing secret.
3. Observe zero signature failures for one full event cycle.
4. Remove old secret.

## Dedupe + idempotency

Use `event.id` as dedupe key.

Recommendations:

- retain dedupe records for at least 7 days
- store payload hash for anomaly detection (`same event.id`, different body)
- enforce downstream unique constraints where possible

## Observability contract

Log and metric tags for every delivery:

- `X-Request-Id`
- `event.id`
- `event.type`
- `event.requestId` (originating API request, when present)
- signature present/verified flags
- enqueue success/failure
- end-to-end latency

## SLO targets (recommended)

- ingress ACK p95 < 500ms
- worker success rate >= 99.9%
- replay success rate >= 99%
- DLQ growth = 0 sustained

## Incident matrix

| Symptom | Likely cause | Immediate action | Long-term fix |
| --- | --- | --- | --- |
| Signature failures spike | Raw-body mutation, stale secret, clock skew | Fail closed, disable problematic deploy, validate NTP/secret | Add dual-secret rotation + raw-body tests |
| Duplicate side effects | Missing dedupe or non-idempotent writes | Enable event-id dedupe gate | Add DB uniqueness + idempotent workers |
| ACK latency/timeouts | Business logic in ingress path | Move work to queue and ACK after enqueue | Hard timeout + queue health alerts |
| Repeated worker failures | Poison-pill event | Route to DLQ and quarantine | Add typed validators + replay tooling |

## Replay + DLQ playbook

1. Inspect failed event payload and worker logs.
2. Patch code/config issue.
3. Replay from DLQ using original `event.id` context.
4. Verify no duplicate side effects.
5. Close incident with root-cause and preventive action.

## Beta caveats

During internal beta:

- signatures may not be enabled for all accounts/environments
- automatic retries may not be fully enabled yet

Engineering rule: build as if full signing + retries are already active.

## Validation checklist before go-live

- [ ] raw-body signature test fixtures pass
- [ ] replay-window validation enabled
- [ ] dedupe by `event.id` in persistent store
- [ ] async queue path in place; ingress is thin
- [ ] DLQ + replay tool available
- [ ] alerting on signature failures, enqueue failures, DLQ growth
- [ ] on-call runbook includes event/request correlation fields

## Framework notes

### Node / Express

- Use raw-body middleware on webhook route.
- Do not verify against parsed JSON.

### Next.js route handlers

- Read raw bytes first.
- Verify signature before `request.json()`.

### FastAPI

- Use `await request.body()` for raw bytes.
- Verify prior to JSON parse.
