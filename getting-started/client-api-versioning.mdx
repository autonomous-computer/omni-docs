# Client API Versioning and Changelog

## Version model

- Base path versioning: `/v1/...`
- Optional request pin: `secapi-version` header
- Response echoes selected `secapi-version`

### `secapi-version` format

`secapi-version` is a date-based pin:

```text
YYYY-MM-DD
```

Example:

```http
secapi-version: 2026-03-19
```

If you omit `secapi-version`, you get the current default behavior for `/v1`.

## When to pin

Pin when you want deterministic behavior across time, especially during beta when the API surface is evolving.

Recommended posture:

- Production integrations: always pin.
- Prototypes: omit pinning, but expect drift.

## Change categories

- Additive: new endpoints/fields, non-breaking
- Behavioral: semantics clarified, may require migration note
- Breaking: removed/renamed fields, auth or error-contract changes

## Change policy

- Breaking changes ship with migration notes
- Deprecations are announced with a notice window before a breaking change takes effect

## Changelog format

For each release:

- Release date (UTC)
- Affected endpoints
- Contract changes
- Migration steps
- Sunset dates (if applicable)
